# 把厨房搭好，再离开厨房：poteto 谈每月数千 PR 背后的智能体工程

> **来源**：[LIVE: Poteto (creator of pstack) on shipping 1,000's of PR's a month at SpaceX](https://www.youtube.com/watch?v=MN9dGgmLyso)
> **频道**：Matt Pocock（直播，约 65 分钟）
> **嘉宾**：Lauren Tan（X：@poteto），曾任职 Meta React 团队、Netflix 与 Cursor，现于 SpaceXAI 参与 Grok Bot 开发，开源 Cursor 插件 pstack 的作者
> **主持**：Matt Pocock，TypeScript 教育者，开源技能库 mattpocock/skills 的作者

poteto 此前发表过一场题为「上个月我如何向生产环境合入 2,500 个 PR」的演讲，在 X 上获得约三百万次观看。这场直播是围绕那场演讲的追问。两人各自维护着一套流行的智能体技能库，Matt 开场称之为「技能派的会师」。

整场对话的主线可以概括为一句话：**工程师的新职责，是经营智能体所处的环境，而不是盯着智能体本身。** 下文按对话顺序整理。

---

## 一、从「盯着一个智能体」开始

poteto 离开 Meta 后休息了一个月，用 AI 写一个业余项目。她很快发现自己陷入一种尴尬状态：花上几个小时，事无巨细地指挥**一个**智能体。那时还没有 Cursor 的智能体窗口，大家各自在终端里搭编排工具。

她因此开始折腾技能（skill），想把自己的工作方式提炼出来交给智能体，让它「写代码、走流程都更像我」。这个早期项目叫 noodle，后来成为 pstack 的雏形。问题在于效果难以衡量，她形容那段时间是「盲飞」。

加入 Cursor 后，她的第一项任务是排查智能体窗口的性能问题，包括卡顿与堆快照分析。她发现自己又成了「人肉代理」：在智能体和 Chrome DevTools 之间来回搬运信息，一切手动完成。也正是在这里，她早期在验证与严谨性上积累的经验重新派上用场。

她对智能体有一个朴素的判断：**即便是最前沿的模型，也倾向于走捷径，做最容易的那件事。** 因此她的技能设计只有一个目标：**让最容易的做法恰好就是正确的做法。**

## 二、领域知识没有贬值，反而更重要

Matt 问：AI 越来越强，领域专长是否在贬值？

poteto 的回答是否定的。模型足够聪明之后，**瓶颈不再是智能体，而是人能否把意图和目标清晰地表达出来，让智能体理解并执行。** 一位医生或律师，如果同时对技术足够好奇、熟悉智能体，就拥有构建优秀产品的巨大优势。当下真正的瓶颈，是「意图与愿景向智能体的传递」。

两人在此谈到语言的作用。Matt 观察到，智能体一旦「抓住」某个词（例如 TDD），就会在后续思考中不断强化它。poteto 举了 Matt 提出的「同义反复测试」（tautological tests）为例：一个高度压缩的词，承载了大量含义，用对了词，智能体就能沿着正确方向展开。在她看来，智能体时代是自然语言与编程语言的交汇，「归根结底都是语言，都是沟通」。

## 三、米其林厨房，而不是软件工厂

业界流行用「软件工厂」形容大规模智能体协作。poteto 不喜欢这个说法，因为「工厂」唤不起品质与匠心，而这恰恰是技术人看重的东西。她更愿意用「米其林厨房」作比。

做饭既可以只为果腹，也可以升华为艺术。这个隐喻恰好对应信任阶梯的两端：

- **家庭厨师**一个人包揽备料、烹饪、清洁。往厨房里多塞几个家人，多数人只会更手忙脚乱。
- **主厨**并不亲手做每一道菜，而是厨房的技术负责人：订购食材、安排储存与备料、把控节奏。这是一份「不只是做饭」的工作。

今天的工程师正处在同样的位置：代码不再由自己逐行书写，但**最终结果仍由人负责，署的仍是人的名字，押上的仍是人的声誉。** 技能、环境、代码库的组织方式，就是构建产品的「新食材」。

## 四、验证：工具箱里最重要的技能

Matt 认为，多数人把模型当作黑箱魔法，不相信自己能改善智能体的表现；poteto 则始终在为智能体打造验证工具。

poteto 的表述非常直接：**验证是工具箱里最重要的一项技能。** 验证意味着给智能体「装上手和眼」：它能运行自己写的代码，像真实用户一样与之交互、调试、抓取 trace 和快照。

这是她加入 Cursor 后构建的第一个技能，也是攀登信任阶梯的关键一步。在此之前，她写过的 how、why、unslop 等技能都受限于同一个问题：人仍然夹在智能体与结果之间充当中转。智能体看不到自己工作的结果，就无法迭代；**验证是任何循环里最重要的一环。**

她的第一个用例是性能优化中的「爬山」（hill climbing）：给定评分标准，智能体在循环中持续改进分数。Karpathy 的 Auto Research 项目体现的也是同一种思路。如今在 SpaceXAI，每个应用都有一个自动维护的验证技能，已经成为「关键基础设施」。

## 五、把确定性的部分交给脚本

poteto 还为验证专门写了一套 CLI。这个做法源于早期对上下文窗口的焦虑：当时的压缩与摘要效果很差，普遍认为摘要会让智能体「变笨」，节省上下文因此至关重要。

她把智能体的工作看成一条光谱：

- 一端是**判断型**任务，需要整合上下文、权衡设计；
- 另一端是**确定性**任务，例如把代码从一种模式机械地重构成另一种，智能体无需每次重新构思。

此前她观察到，智能体每次做验证都在「从零重建世界」。于是她把确定性的部分固化为脚本和 CLI，技能本身退化为「带少量说明的工具外壳」。核心原则是：**高效分配确定性与非确定性，让智能体只处理真正需要判断的部分。** 代码迁移是典型场景，可以借助 codemod 或 AST 遍历完成。

## 六、工程师的新职责是经营环境

Matt 指出，这种做法实际上是把任务从智能体身上转移到环境中，代码库因此变得「易于修改」。

poteto 说得更明确：**工程师的新工作，是把时间花在环境上。** 如果不建立信任、不打磨技能与工具，人就会陷入对智能体的微观管理，既耗时间，也无法抵达更高层次的产出。她用「钝刀」作比：明明有更好的工具，却坚持用记事本写代码，一切都会更慢。米其林厨房需要压蒜器这样的专用工具；没有它们，厨师只能临场凑合。

她借用 TypeScript 的**类型收窄**来说明约束的价值：用类型守卫把宽泛的类型收窄成具体类型，代码库同样需要「收窄可能性空间」。

具体到 Grok Bot，她搭建了一个内部框架 Dune，可以理解为面向其 Electron 应用的内部版 Next.js。它的特点是：

- 附带严格的 lint 规则，代码库被设计成「做一件事只有一种方式」；
- 采用约定式结构：每个功能拥有独立目录，系统通过注册表和代码扫描自动发现功能；
- 在这样的环境里，写出坏代码本身就很难。

这样做的收益是双向的，人和智能体都不必再为这些约束分心。智能体要加新功能，直接进入新的功能目录，而不会继续往「上帝文件」里追加代码。这个设计正是被上帝文件逼出来的：Grok Bot 早期版本由八个至少上万行的巨型文件构成。

她的关键习惯是：**观察智能体如何失败。每次看到错误或可改进之处，就追问：怎样把它变成一条 lint 规则？怎样让代码库从结构上杜绝这种错误？**

Matt 的总结很精炼：像鹰一样盯着智能体，把它们的错误转化为环境规则。环境的好处在于不必往智能体脑子里塞规则，它们撞上规则，自然会弹回来。

## 七、内循环与外循环：把自己从链路中移除

Matt 追问规模化的机制：两千五百个 PR，难道是开了两千五百次对话？

poteto 首先强调前提：没有前面花在「厨房、刀具和工具」上的时间，高产量无从谈起。她把第一套环境比作开好第一家餐厅：餐厅运转良好之后，人就不必一直守在店里，可以像戈登·拉姆齐那样，把诀窍传给行政主厨，再开第二家、第三家。每个大型项目就是一家餐厅，她在多家之间「直升机式」巡视。

接下来是**内外双循环**：

- **内循环**：智能体围绕她的意图（或者说意图的一份快照）写代码。
- **外循环**：Slack、Linear、X 上不断涌入的 bug 报告、功能请求、后端限制。

快照会过期，新信息会出现。如果没有把外部信息拉进内循环的触发机制，人就只能亲自充当搬运工。Grok Bot 这类带有邮件、日历、Slack 等连接器的个人智能体，可以自动化外循环；把两个循环接通，威力巨大。

例如让智能体订阅一个 Slack 频道：收到 bug 报告后，自行分诊，用预先搭好的验证技能复现，确认问题确实存在于主分支，而不是用户配置、数据或依赖导致的。

她反复追问自己一个问题：**在这个流程中，我在哪里是瓶颈？智能体为什么需要我来回答这个问题？** 目标是让智能体基于真实数据自己找到答案，而不是靠猜。所谓「公司大脑」「上下文图谱」，在她看来并不复杂：把原本要人手动传递的信息，教会智能体自己去取，从而「把我从等式中移除」。这与 Netflix 的管理原则「给上下文，不给控制」一脉相承。

在工具层面，她的组合是：Grok Bot 作为外循环，监听 Slack、X、邮件和 Linear；发现问题后直接投递给 Cursor 的「项目」（projects）功能。项目是运行在云端、拥有独立电脑的**协调者智能体**，相当于行政主厨或幕僚长：它本身不干活，而是委派、编排、监督子智能体。

Matt 问：如果一下涌入三十个问题呢？poteto 的回答是，协调者拿到全部载荷后，自行决定最高效的分配方式。更重要的是，**相关的任务应当放进同一个项目**。如果一波性能投诉同时到来，它们很可能彼此关联；每个问题各派一个智能体，就会丢失线索、重复劳动，也看不到更高层的根因。多份略有差异的报告放在一起，才能让人「拉远镜头」，看清问题真正出在上游。

## 八、两千五百个 PR 不等于两千五百个功能

poteto 特别澄清：这些 PR 中，相当一部分是**「园艺」**，也就是持续的养护与修剪。在人类工程师众多的团队里，园艺的价值在于维持一个让所有人受益的环境，尤其是缺乏上下文的新人。好的环境能让新人从第一天起就提交高质量代码。

PR 的另一个来源是**读代码**。她有一些例行任务，例如让一个智能体持续扫描 React 代码中的「踩脚枪」（footgun，即容易误用的写法）。有意思的是，她不让智能体立即修复，而是**把发现追加到一份文档里**。每隔几天她翻看一次，常常发现「这些其实是同一个问题」。

缓冲区或队列，有时比为每个问题派一个子智能体更有效。纯执行模式容易只见树木，而积累下来的产物迫使人用判断力（或另一个智能体）识别模式。这正是幕僚长型智能体的价值：**它既能执行，也能看见森林。**

## 九、抽检，而不是逐一品尝

Matt 换了个问法：两千五百道菜从你面前经过，你都尝了吗？

poteto 坦言做不到。完全不尝当然不行，但规模化之后，重点转向**抽样**与**流程**，就像工厂车间的质检员不会检查每一件产品。她会严格审视抽到的 PR 与代码，寻找低效和坏模式，然后**修正环境，而不是修正某一个智能体**。

偶发问题可以放过；但如果多个智能体犯了同样的错误，走了同样的捷径、传播了同样的变通写法，那就说明「厨房」需要改造：调整技能、约束、linter、类型系统，确保问题不再出现。改造足够多次之后，环境会把所有人引导得足够好，人就可以抽身离开。「这是理想状态。」她也承认，这一步非常难，装上 pstack 并不能自动做到，需要长期投入，思考代码，思考智能体在哪里失败，有意识地设置护栏。

## 十、「黑灯工厂」与夜间合并

Matt 问：这算不算「黑灯工厂」，也就是完全无人值守的工厂？

poteto 说：某种意义上算。她的智能体会自行合并 PR，二十四小时运转。她手下相当于有十多个「幕僚长」，分别负责 Grok Bot 桌面应用的性能、用户 bug 修复，甚至出于兴趣用另一种语言重新实现某些模块。

她在 PR **合入之后**再做审查。pstack 有一个「全自动驾驶」（full autopilot）指令，会触发一套严格的验证循环：为每个 PR 启动多个验证者智能体做模糊测试，真正运行应用，像人一样四处点击，寻找回归和 bug，发现问题自行修复，反复直到 PR 可以合入。这个过程很耗 token，但可以调节，比如把十个验证者减为一个。

**验证加上环境，给了她足够的信心说：「去合并吧，我明早看提交记录。」** 发现问题就回滚、修改、补 lint 规则。

第一次打开这个开关时，她非常害怕，担心一夜之间引发严重事故。「那需要相当的勇气。」如今智能体在她睡觉时合并代码，她说自己「睡得好多了」。

Matt 补充了一个区分：一种「黑灯」是代码几乎不存在、人忘了代码这回事，比如 Karpathy 所说的氛围编程（vibe coding）；poteto 的路线恰恰相反，代码和环境是根本，环境糟糕，输出必然糟糕，即「垃圾进，垃圾出」。poteto 认为，与其说黑灯工厂，不如回到餐厅的比喻：即便是餐厅老板，也会时不时探头进厨房尝一口。Matt 把这一点概括为**「抽检，而非拦截」**。

## 十一、高风险领域：可验证性决定一切

Matt 问：在医疗、法律这类对安全极其敏感的领域，或者大多数改动都是「单向门」（无法轻易回滚、可能造成数据丢失）的场景，这套做法还成立吗？

poteto 认为，一切取决于**验证的质量**。如果一个领域的工作高度可验证，单向门实际上就能变成双向门，因为验证提供了足够的信心。反之，难以用程序验证的领域就很难做到。软件工程在多数情况下相当可验证；数学的某些方面，例如证明，也可以验证。

她预测未来会出现越来越多面向智能体的编程语言，并提到一种「把编程与证明结合起来」的语言（直播中称为 Bend）。传统上，形式化证明需要用 Lean 或 TLA+ 等单独的语言编写，用求解器检查情形是否覆盖完整、是否存在竞态条件。如果智能体能以极高置信度验证自己的工作，「编译通过，证明也表明它正确，为什么不直接合并？」她也承认，并非所有领域都可验证，这是行业需要共同回答的问题。

## 十二、技能只是写成文字的流程

收尾时，Matt 问：pstack 和他自己的技能库，用户该如何取舍、如何组合？他的看法是，技能源自流程，本质上是「被写成文字的流程」。

poteto 认为两套技能高度互补。技能「只是英语，只是 markdown」，每个人应当按自己的方式编织组合。她又用了厨师的比喻：每位主厨都随身带着自己的刀，那是他们亲手磨过、信得过的工具。有人会把 Matt 的 grill-with-docs、wayfinder 与 pstack 的执行类技能搭配，有人会偏重其中一套，归根结底是对工具和作者的信任。

她给出的具体建议是：**翻看自己与智能体的历史对话记录。** 那些反复纠正、不得不介入的地方，就是流程具象化的现场，是「上下文的宝库」。从中提炼更高层的经验，写成可复用的技能或新的 lint 规则，智能体就不会重复同样的错误。pstack 中的 recall 技能就来自这样的经历：她在 Cursor 做虚拟列表时，需要把旧的修 bug 对话中的上下文带进新对话，于是把这套操作压缩成了一个技能。

她还观察到技能本身的演变：早期技能更关注实现细节，比如具体执行哪条脚本命令；随着模型能力提升，技能越来越多地描述工作流，成为一系列步骤。她预测技能会变得越来越小、越来越紧凑，也越来越容易组合，比如把 wayfinder 与 poteto-mode 拼成一个自定义模式，「因为它只是语言」。

Matt 的结语是：技能并不神奇，它只是文字，是有人事先完成了思考，把抽象的流程转化成了语言。一旦这份思考完成，任何人都可以使用。

## 整理者附记

这场对话的价值不在于「两千五百」这个数字，而在于数字背后的因果链条：**验证让单个智能体值得信任，环境让信任可以复制，内外循环让人退出瓶颈位置，抽检与环境修正让质量在规模化中不被稀释。** 每一环都以前一环为前提，跳过任何一步直接追求并行数量，结果只会是成倍放大的混乱。

对于非纯工程岗位而言，其中两点同样适用：一是「修正环境，而不是修正某一次产出」，把重复出现的问题沉淀为规则；二是从自己与 AI 的历史对话中提炼流程，把反复的人工纠正转化为可复用的技能。
